# Configuration and persistence

The [user configuration guide](../user/configuration.md) owns the preference reference. The implementation is [settings.h](../../src/config/settings.h), [settings.cpp](../../src/config/settings.cpp) and [ViewPreferenceWriter](../../src/config/view_preference_writer.h). [preference_schema.h](../../src/config/preference_schema.h), included only by settings.cpp, holds the schema: each preference's TOML name, accepted values and BrowserSettings field, in `BrowserPreferenceId` order, which a `static_assert` checks.

Workbench preferences are flat `browser.workbench_*` keys in the same files, so Reset all settings and the writer's coalescing cover them. Their bounds are named in [directory_options.h](../../src/model/directory_options.h) because `config` cannot include `workbench`; they match what `sanitizePaneState` and `normalizeWidths` in [src/workbench](../../src/workbench/pane_layout.h) keep, and the settings suite checks each edge against those functions, so a value the layout would refuse cannot be saved. A stored `0` stands for an absent size.

## Ownership and reload

Built-in defaults are overlaid by the optional base `config.toml`, then writable GUI `settings.toml`. GUI edits never modify the base. Canonical names have one spelling. Runtime loading warns about unknown root/browser keys and decodes recognized preferences normally. The validation CLI remains strict about unknown keys and checks one required file, with no adjacent overrides and no compositor initialization. Wrong types, unsupported known values, incompatible schema versions and malformed TOML still fail. Schema version is integer 1 when supplied. This policy applies to configuration files, not the separate Places state schema.

The worker serializes typed edits and reload requests, coalescing pending edits per preference. Saves reread and validate actual persisted inputs before merging only the requested keys. The override document retains unknown values, arrays and tables while known preference fields are replaced or removed; comments and original formatting are not retained on a changed save. No-op saves preserve the exact bytes. Removing an override restores inheritance. Reset removes only recognized preferences, preserving unknown values for another application version. An invalid reload keeps the last valid snapshot; failed saves reload actual persisted state. Publish only after pending edits/reloads drain.

File monitors follow canonical files, existing path components and resolved declarative targets. Coalesced events trigger worker reads; the read after watch installation closes the read/install gap. Callbacks publish during Update. Only relevant global changes should replace a live preference; an unrelated reload must not reset the current visit's view/zoom/history state. Ordinary close drains pending preference saves.

Explicit sort changes from menus, list headings and the open Settings dialog share BrowserPage's sort application path. They preserve model selection IDs and request the beginning of the new order. Layout consumes that request after preference notifications and view switches, clearing any intervening captured scroll anchor or pending history viewport before arranging the virtualized cells. Ordinary reloads and unrelated preference changes retain their existing viewport behavior.

## Palette sources

[choosePalette](../../src/ui/palette_source.h) picks the palette; [PaletteWatcher](../../src/app/palette_watcher.h) applies it and again after every change. With `color_scheme = "auto"`: `colors.toml` when it exists (an invalid file is logged and leaves the current palette), else the desktop's GTK 4 colors when [desktopPalette](../../src/ui/desktop_palette.h) finds them usable, else the built-in palette. `"dark"` and `"light"` never read GTK files. The log gets one line each time the source changes.

[readGtkColors](../../src/ui/gtk_colors.h) reads `$XDG_CONFIG_HOME/gtk-4.0/gtk.css`. It follows `@import url("x");`, `@import url(x);` and `@import "x";` for relative paths (to the importing file), absolute paths and `file:///` URLs (percent-decoded); other schemes are ignored. It collects `@define-color NAME VALUE;` and `--name: VALUE;` in any block into one table in document order, an import being read at its position and a later definition winning; `--accent-bg-color` and `accent_bg_color` are one name. Values are `#rgb`, `#rrggbb`, `#rrggbbaa`, `@name` and `var(--name)`, with a trailing `!important` ignored; a name with any other value is undefined. Strings and `url(...)` contents are skipped, so a definition written inside one is not read. Unknown constructs are skipped without a message. A missing or unreadable root means no desktop colors.

Bounds: import depth 4, 16 files, 1 MiB per file (a larger file is skipped whole), reference chains 8 deep. A path is read once, so import cycles end; only regular files are read (links to them are followed).

| Palette role | GTK name |
| --- | --- |
| `primary`, `on_primary` | `accent_bg_color`, `accent_fg_color` |
| `surface`, `on_surface` | `window_bg_color`, `window_fg_color` |
| `surface_container` | first of `card_bg_color`, `popover_bg_color`, `sidebar_bg_color`, `headerbar_bg_color` |
| `outline_variant` | `border_color`, else `sidebar_border_color` when it differs from the surface |
| `hover`, `on_hover` | `active_toggle_bg_color`, `active_toggle_fg_color` |
| `error`, `on_error` | `error_bg_color`, `error_fg_color`, else `destructive_bg_color`, `destructive_fg_color` |

The colors are usable only when `window_bg_color`, `window_fg_color` and `accent_bg_color` are defined and the first two are opaque; a translucent window color is not a surface the derivations can reason about, so the built-in palette applies. A color the theme gives is never changed. The other roles are derived from it, with S the surface, T the text color and `mix` a mix in Oklab, so equal steps look equal in every hue and brightness. The palette is dark when the surface is darker than the text. Contrast figures are WCAG ratios.

| Role | Derivation |
| --- | --- |
| `secondary`, `tertiary` | the primary color with its hue turned by 30 and 60 degrees and its chroma scaled by 0.85 and 0.9, moved toward T until 3:1 on S |
| `error` without an error color | the built-in error color of the dark or light variant |
| `*_container` of primary, secondary, tertiary, error | `mix(S, color, 0.30)` |
| `on_*_container` | the color moved toward T until 4.5:1 on its container, else black or white |
| `on_secondary`, `on_tertiary`, `on_error` and `on_primary`, `on_hover` when not given | whichever of T and S reads better on the fill, else black or white when that is under 4.5:1 |
| `surface_container` without a given one | `mix(S, T, 0.07)` |
| `surface_container_low`, `_high`, `_highest` | `mix(S, C, 0.5)`, `mix(S, C, 1.5)`, `mix(S, C, 2.0)` for the container C (a container within 0.01 of S uses the 0.07 step), shortened where T would read under 4.5:1 |
| `on_surface_variant` | `mix(S, T, t)` from t = 0.55 in steps of 0.05 until 3:1 on S, on the highest container and on `primary_container`, the fill of a selected row |
| `outline_variant` without a given one | `mix(S, T, t)` from t = 0.16 in steps of 0.02 until 1.25:1 on S and on the container; a quiet line stays visible without outweighing the 7% container step |
| `hover` without a given one | `mix(S, T, 0.12)` |
| `shadow` | dark: `mix(S, black, 0.5)`; light: T |
| `scrim` | black |

[GtkColorWatch](../../src/app/gtk_color_watch.h) watches, only while the desktop colors are in use, the folder of the root `gtk.css` and the folder of every file the reading tried, read or not, so a stylesheet written after `gtk.css`, or in a folder created later, is seen. A folder that does not exist is stood in for by its closest existing ancestor. For a path that is a link, or sits under one, the folder of its resolved target is watched too, so an edit in place of the target is seen; a target folder that is the same directory as the path's own folder (a linked parent) is watched once. A monitor is kept only while its path still names the directory it started on, compared by device and inode at every reload; a different directory (a link repointed, or a folder replaced by one with another inode number) gets a new monitor after the old one is dropped, and that counts as a change of the watched folders. A folder made again under an inode number the old one freed is not told apart this way; the file monitor's own recovery then finds it, within seconds. When a watched folder is itself a link, the folder that holds the link is watched too, so repointing the link reloads the colors. At most 8 folders are watched, the root's first and the folders that hold links last; one log line says when more were wanted. A change to a path tried, to the root's folder or to an ancestor of a missing folder goes through PaletteWatcher's 100 ms debounce and reload. When a reload changes the set of watched folders it reads once more, so a write that landed between the first read and the new watches is not lost; that second read starts no third. Creating or removing `colors.toml` is seen by the existing watch of the Luciole config folder.

## Settings layout

[SettingsController](../../src/app/page/settings_controller.cpp) retains the preferred 880-pixel dialog width independently of the opening window size. The common popup layout in [BrowserPage](../../src/app/page/browser_page.cpp) calls `layoutDialog()` before measuring Settings on each requested layout. It reapplies the parent-constrained height up to 640 pixels and the compact navigation breakpoint. Parent configuration already requests popup layout and recenters the dialog. Resize the existing view so its category, scroll state, focus and drafts survive; dismiss an open select dropdown when its anchor geometry changes. Do not persist the temporarily constrained popup dimensions as its preferred size.

## Filename presentation

`browser.filename_truncation` accepts `middle` (default) and `end`. Settings → Views → Long Filenames uses the existing typed preference and Select control. BrowsePresentation carries the value to every pane; FileRow and FileTile apply the Label ellipsis mode on bind, including recycled List rows, expanded folders, Miller columns and Grid tiles. Grid keeps its two-line wrapping and applies the preference to overflow. Parent labels, metadata columns, Places, tooltips and raw operation names retain their existing behavior. Sorting, selection and metadata loading are independent of the preference.

Plain single-line Middle text uses the shared renderer's compact layout. Pango stretches its synthetic ellipsis run after removing whole grapheme clusters; the renderer subtracts that excess advance from the layout budget and asks Pango to lay out again. It uses public APIs without rewriting filenames or modifying Pango-owned glyph data. Actual spaces remain text. Start/End, markup and multiline layouts retain normal Pango behavior. The correction lives upstream in Noctalia and is mirrored into Luciole.

## Typing and query scope

`browser.typing_mode` accepts `search` (default), `filter` and `typeahead`. The Settings General page uses the existing Select control for all three. Search and filter typing, including input-method commits, use the same toolbar field; current-folder mode updates its placeholder and tooltip. Explicit field entry and Ctrl+F use that same scope. Typeahead retains recursive explicit search. Preference changes update every existing pane and Miller controller.

[BrowserController](../../src/browser/browser_controller.cpp) owns the scope. Recursive queries keep their 175 ms debounce and worker traversal. Local edits project the current DirectorySession listing through DirectoryModel’s folded literal name filter, without starting traversal or re-reading the folder on each keystroke. Session monitor updates remain visible under the filter; refresh, navigation history and duplication retain the scope. Filtering temporarily projects only the root listing when expandable list folders are enabled. Mode changes cancel pending recursive work before publishing the appropriate source. Miller child and ancestor controllers inherit the source scope.

## Drop action

`browser.drop_action` accepts `menu` (default), `copy` and `move`. Settings → General → When Dropping Files uses the typed preference and Select control. [DragDropController](../../src/app/page/drag_drop_controller.cpp) resolves the same value for internal drags, external drop targets and the drag cursor. Ctrl, Shift and Alt keep priority over the preference, and Trash, items from Trash and non-native folders keep their existing fixed behavior. `menu` sets `DragAction::Ask`, so [TransferController](../../src/app/page/transfer_controller.cpp) shows a drop action context menu anchored at the drop point through [MenuController](../../src/app/page/menu_controller.cpp), offering Copy Here, Move Here, Create Link Here, Extract Here and Move into New Folder… with one shared cancellation path.

## Atomic writes

[atomic_file.cpp](../../src/fs/atomic_file.cpp) implements anchored local transactions. Cooperating writers use a persistent advisory lock. Preserve that lock across ordinary cleanup; unlinking it can split writer coordination. New private directories use 0700 and data/temporary/lock files use 0600.

Writes use an exclusive neighboring temporary, file flush, destination revision recheck, atomic publication and parent-directory flush. First creation must not replace an unexpected destination. Reject unsafe sidecar targets, including symlink/hard-link, foreign-owned, special and read-only files. Declarative base symlinks remain readable under the loader's separate rules.

Outcomes distinguish unchanged, not committed, committed but directory synchronization failed, and durable. Report visible-but-not-durable commits accurately. Cleanup removes only the transaction's own temporary. This protects cooperating writers and ordinary races; it does not promise atomic exclusion of an uncooperative same-user writer between a final check and rename.

## State and caches

[SharedBookmarks](../../src/config/shared_bookmarks.h) owns the GTK-compatible `$XDG_CONFIG_HOME/gtk-3.0/bookmarks` document. [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-bookmark-list.c), [Nemo](https://github.com/linuxmint/nemo/blob/master/src/nemo-bookmark-list.c) and [GTK](https://github.com/GNOME/gtk/blob/main/gtk/gtkbookmarksmanager.c) use this URI-plus-optional-label format; GTK 4 continues using the gtk-3.0 path. The older HOME/.gtk-bookmarks is a read fallback until a modern document is seen. User bookmarks are authoritative there, without importing old Luciole pins. Valid native/remote URIs and labels are read without probing destination availability. Display is deduplicated; opaque, unsafe, duplicate and overflow records remain in the document when unrelated bookmarks are edited. Credentials are never copied into Luciole state or shown in bookmark labels.

[PinService](../../src/browser/places.h) serializes worker reads/writes and projects shared user bookmarks into the built-in Places layout. [StateStore](../../src/config/state_store.h) retains that layout and optional last-window tab state with separate revisions. Cached custom rows are placement slots only: shared order/labels replace them and deleted shared rows cannot be resurrected from state. Built-in rows are not seeded into the shared file; an explicitly shared built-in URI is shown once and its label is honored, except protected Trash. The shared file supports 256 displayed bookmarks; layout storage allows those plus at most eleven built-ins. Overflow records remain untouched. No state schema or migration marker is added.

[FolderViewService](../../src/browser/folder_views.h) owns per-folder sort and view mode for the whole application. It reads and writes [FolderViewStore](../../src/config/folder_view_store.h) (`folder_views.toml`) on a serial worker and answers lookups from memory. `BrowserController` keeps the default sort and view mode apart from the effective ones and applies the current folder's settings in `loadVisit()`. It does that only while `browser.remember_folder_views` is on; with it off, `loadVisit()` leaves the sort and view mode unchanged. Every change, load or enable switch runs the service's changed callback. `WorkspaceApplication` passes that to each page, whose [FolderViewController](../../src/app/page/folder_view_controller.h) re-applies the folder settings to the page's controller and Miller columns. The same controller decides whether a sort or view change goes to the current folder or to the defaults. Column view stays a window-wide default and ignores folder view modes. While folder views are on, a page follows the mode of the folder it shows, or the default for a folder with none, on a history visit and on a change of the service alike (`viewModeAfterVisit`); with them off, a page in Workbench stays in Workbench on a visit. A folder view mode is Grid, List or Workbench; the store reads `list`, `grid` and `workbench` and refuses any other value with an issue, which drops that entry. `BrowserPage::options()` seeds new pages with the defaults, not the current folder's settings. File picker pages get no service, so they neither read nor write folder settings and keep their `chooser_*` sort and view mode.

Bookmark icon overrides are private state attached to the cached bookmark row by URI. `combine()` carries them onto matching shared rows while shared labels and ordering remain authoritative. The GTK file writer compares and preserves only URI and label, so an icon-only edit does not rewrite shared bookmark contents.

Directory watches cover the shared/legacy files, parent replacement, missing directories and resolved symlink targets. A 50 ms debounce coalesces reloads; changes arriving during worker I/O request another serial reload. New target watches trigger a re-read to cover handoff. Shutdown disconnects watches and cancels the debounce, while already queued writes finish without UI callbacks. Read errors preserve displayed rows and disable edits until reload succeeds. Session-save errors remain independent.

Shared reads are bounded to 256 KiB and require a stable regular file; managed symlinks can be read. Writes reuse the checked atomic writer, require an owned writable regular file without links, retain untouched URI/label bytes and compare the document before replacement. Stale UI proposals are rejected after reloading both sources. The shared commit precedes local layout persistence; a layout failure reports an error without pretending to roll back the shared commit. There is no transaction across both files, or atomic exclusion of an uncooperative same-user writer in the final check-to-rename window. Do not conflate settings, Places/session state, future operation journals and regenerable thumbnails. Credentials do not belong in configuration, state, URI history or cache identities.

[VisitStore](../../src/config/visit_store.h) keeps visit counts under `$XDG_STATE_HOME/luciole/visits/`, separate from `state.toml`, whose strict schema would make older builds reject new keys. A location is filed by the FNV-1a hash of its URI into one of 32 files, `00.tsv` to `31.tsv`, so every process agrees where it lives. Each file is the line `luciole visits 1` followed by one line per location: count, last visit in Unix seconds and URI, separated by tabs, sorted by URI. A file holds at most 625 locations and stays within the 256 KiB private file limit, so the store holds at most 20,000; when a write would exceed either bound, the file keeps its most recently visited locations. URIs pass `storedUriProblem`, are at most 4096 bytes and contain no control characters. A file that has a malformed header, a malformed or duplicate line, a location hashed to another file, or too many lines reads as empty and adds an issue; the next write to it replaces it. A file whose header names another format version, `luciole visits N`, reads as empty and is never written, so a build that does not know that version keeps the counts of the one that does. A file that cannot be read, because it is larger than 256 KiB or is not an owned regular file without links, reads as empty and is left as it is; every write to it is refused with an issue until the user removes it. A write that finds a file locked by another process is refused with an issue too. Writes go through `updateTextFileAtomic`, which rereads the file under its lock, so counts from another process are summed, never overwritten; counts saturate and the later time wins.

[VisitService](../../src/config/visit_service.h) owns the store on a serial worker and never touches the disk on the main loop. It loads every file once, keeps the saved counts per file plus the visits being written and the visits not yet written, and answers reads from those three. A recorded visit calls the changed callback from the main loop, once for all the visits recorded within about a frame. A visit is written once recording pauses for two seconds, at most eight seconds after the first unsaved one, or at once when 256 distinct locations wait. A failed write is reported in `warning()` and its visits are dropped. Turning `browser.record_visits` off drops unsaved visits and makes every read empty. `clear()` advances a generation so results of work started earlier are ignored, then rewrites each existing file without locations; a file it cannot rewrite keeps its counts, which appear again once the clear finishes, and is reported as not cleared in `warning()`. Destroying the service still writes unsaved visits; the worker holds its state until it finishes, without callbacks.

Folder entries come from [BrowserController](../../src/browser/browser_controller.h)'s entered callback, which fires for open, back and forward once the session for that history entry first reaches Ready. A folder that fails to load or is left before it loads, a refresh and a duplicated history are not entries, and `skipPendingEntry()` drops the entry still loading. Miller column controllers set no callback, so moving through Column view records nothing. File opens are recorded in [BrowserPage](../../src/app/page/browser_page.cpp) where every user activation reaches the page's `FileLauncher`: `platform` cannot depend on `config`, and the launcher also opens links that are not visits. [WorkspaceApplication](../../src/app/workspace_application.cpp) owns the one service, applies `record_visits`, gives the recorder only to pages of browsing windows, so FileChooser portal windows record nothing, and skips the first folder of a page that reopens one: a tab restored by `restore_last_window`, and a new tab, pane or window that shows the current folder again. It flushes when the last window closes and stays alive while the service is busy.

The shared thumbnail cache and Luciole' ownership ledger are regenerable. Pruning must preserve untracked entries and foreign replacements. A future operation journal has different ordering/recovery requirements; cache persistence is not an implementation of crash-safe file-job recovery.
